Framing

Why "OS for LLM" — not another LLM wrapper?

Multi-agent LLM systems today are mostly Python scripts on Linux. The OS sees them as one opaque process tree — no isolation, no priority for critical work, no quota enforcement. We claim agent orchestration is an OS problem.

The thin-wrapper trap
The course guideline explicitly disqualifies projects where the OS angle is only "it runs on Linux." We took that seriously and modified the xv6 kernel itself — not the userspace around it.
First-class kernel entities
Each agent should be a kernel-managed process with its own role, priority, and signal handling — scheduling, IPC, and isolation come from the kernel, not from a userspace library.

Part 1 · LLM Architecture

Five cooperating agents, one supervisor

  • parser — turns one raw log line into a structured record.
  • classifier — assigns level (INFO / WARN / ERROR / CRITICAL).
  • root-cause — runs only on ERROR / CRITICAL items.
  • fix-suggester — proposes a remediation plan.
  • evaluator — quality-checks the previous output and can demand retries.
  • All five hit the same backend: Upstage Solar Pro 3 through one Proxy Daemon on the host.
Part 1 · Supervisor Pattern

Why an evaluator? — LLM output is non-deterministic.

  • Implemented with xv6 kill() + sleep/wakeup, not a Python while loop.
  • Bounded retry: max 3 attempts, then surface failure to the orchestrator.
  • Demo trace confirms the loop firing — three EVAL_RETRY events followed by evaluator:FAIL on stubborn lines.
  • This is a real OS-level signaling + synchronization problem.

Rule of thumb: if it could have been multiprocessing or cgroups, we did not use it. 11 new syscalls shipped (nos. 22–32) — from setrole(2) / agentstat(2) introspection through the verify+rollback (27–29) and semantic-cache (30–32) families — plus a userspace priotest. Pattern A: kernel verifier guards every LLM fix — FAIL → checkpoint/restore rollback + retry; PASS → accept. Pattern B: FNV-1a exact + MinHash/Jaccard semantic match short-circuits the LLM call before PROXY_REQ is even emitted, backed by a /cache.bin disk overlay.

Part 2 · Host–Guest Boundary

xv6 has no network stack — where does the LLM call happen?

  • xv6 sees only a read / write on a pipe — the LLM is fully abstracted away.
  • live — real Upstage API call.
  • replay — cached responses, used for reproducible measurement.
  • mock — deterministic stub, used for CI and on-stage demo without network.
  • The same xv6 binary works against all three modes — proxy daemon is the swap point.
Part 3 · When to Use Liberal_OS

A fit when you need an agent runtime, not a script.

Post-hoc triage of high-volume streams
Log floods, crash dumps, alert backlogs — workloads that benefit from staged LLM reasoning (extract → classify → diagnose → fix), not a single chat turn.
Strong fault isolation between agents
One agent crashing must not bring the pipeline down. xv6 process isolation gives this by construction; a single Python process does not.
Priority differentiation between work items
CRITICAL logs must preempt INFO. Our modified scheduler enforces this at the kernel level — userspace cannot bypass it.
Platform-level retry & quality contract
The evaluator–supervisor + signal-based retry is a reusable mechanism, not a per-script ad-hoc loop. The platform owns the contract.

Not a fit for: real-time chat assistants, single-agent toolformer flows, or any workload that comfortably fits in one process.

Backup · For Q&A

Limitations and what comes next.

Known limitations

  • Filesystem writes are limited to the kernel semantic cache (/cache.bin, via the inode API). Agent-context persistence — checkpoint/resume of an in-flight pipeline, swap-out of an idle agent — remains F-01.
  • Live-mode benchmark at BENCH_N=5 is still a human-run step (T-62); reported numbers use replay/mock for reproducibility.
  • retry_context is recorded, not yet re-fed. Host accumulates violation reasons into injected_sample / retry_context JSON fields, but does not yet thread them back into the model prompt — line-accumulated PROXY_RES frames can desync the wire format, and the kernel cache would short-circuit the re-issued prompt. Fix is guest-side prompt embedding (STATUS §5 future).
  • Single-host scope — no multi-node scheduling; agents share one xv6 guest.

Future work

  • Planner-executor agents on top of the current static DAG.
  • Proxy multiplexing for higher live throughput.
  • RAG / ReAct loops as additional agent roles.
  • Deepening fs as a first-class agent-state store (F-01).
